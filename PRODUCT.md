# DocuGen product context

Otterview DocuGen combines a knowledge workspace with Word template filling and document generation. The user chose DocuGen as the public product name on 2026-10-19 and authorized integrating the former Quill repository into https://github.com/otterview-labs/DocuGen. Quill's Python namespace and runtime configuration names remain compatible with existing installations.

The first delivery is a functional integration for a single shared workspace. Users import and organize source files, inspect extracted content, retrieve facts, fill Word templates and generate documents with source records. Following the initial integration, the user requested a richer knowledge workflow and a full visual upgrade. The knowledge surface and shared shell initially used a reading-workbench direction, later extended to writing and template workflows with selected VoltAgent/awesome-design-md references. That visual identity was explicitly superseded on 2026-10-20; existing backend contracts remain in use.

Assumptions for this first iteration: Chinese interface, local/self-hosted use, manual confirmation of generated documents, no independent user accounts. No claim of production hardening or public licensing readiness is implied.

Local access was simplified on 2026-10-18 at the user's request: leave the optional workspace access key empty to use the loopback deployment directly in fresh tabs. Connection settings appear only for a deployment that requires authentication. Shared-key protection remains available for network sharing; model-provider credentials remain independent server configuration.

An existing host-local model was subsequently exercised with synthetic knowledge and document data, without a model API key. The workspace supports an optional provider reasoning-effort setting for direct answers. Actual knowledge answers with source IDs, AI template variables, outlines and completed DOCX jobs were checked; this is bounded local-model acceptance, not a claim of universal factual accuracy or optional knowledge-engine provider readiness.

The user subsequently rejected the claim of visual unity and identified buttons, typography and colors as the concern. Core routes now use shared Vue controls, page headers, notices, empty states and tabs. Canonical visual properties live in `frontend/src/styles/ui.css`; page styles arrange these controls without redefining their appearance. Cross-route computed-style checks supplement functional and visual checks. This acceptance scope concerns the inspected core routes, not a declaration that the entire open-source product is release-ready.

The knowledge capability expansion (2026-10-17) maps every mounted knowledge-content API path to a product task, grouping HTTP aliases instead of adding duplicate controls. Import/parse, stored chunks/analysis, graph, settings and advanced retrieval join the existing document/source workflow. Availability reflects registered routes and configured prerequisites, with provider failures kept explicit. This is capability coverage, not acceptance of unconfigured model quality or optional multimedia parsers.

The subsequent full knowledge polish retains that coverage and the accepted visual system. Seven tabs and all 28 operation entries use consistent icons; desktop forms group compact controls while mobile operation selection collapses and moves focus to the chosen form. Chinese native file picking supports drag/drop and readable selected-file feedback. Results prioritize source prose and status while retaining identifiers in disclosures. No new provider capability or model-quality claim is introduced by these presentation changes.

A hands-on project-to-template walkthrough exposed integration gaps missed by the earlier isolated tests. Template-assisted retrieval now falls back to bounded field-name keyword queries when the full template has no matches; returned source records remain real and collection-scoped. Spaced placeholders render consistently, and explicit variable refresh reparses the saved template without clearing confirmed values of surviving fields. At that stage browser-reload draft recovery was incomplete; the bounded recovery added below supersedes that limitation for the dedicated template editor. Template rename/delete and generation cancellation remain incomplete.

## Current visual direction — 2026-10-20

The user rejected the warm-green sidebar and selected “Vue 模板市场：深蓝顶部导航、白色内容卡片、蓝色按钮”. The current UI restores the original DocuGen Vue visual family across knowledge, writing, templates, Word import/filling and generation: navy horizontal top navigation, a bold sans wordmark, white cards on a cool gray canvas and blue actions. This user decision replaces the earlier reading-workbench identity; earlier polish and reference decisions remain historical context. `DESIGN.md` and `.impeccable/design.json` describe the actual replacement implementation.

The restoration adapts the original application's visual family to the expanded functional scope; it does not promise a pixel-exact reproduction. All twelve authentic starter DOCX covers and their provenance remain intact, along with seven knowledge tabs, 28 operation entries, optional authentication and the shared control contract. The reviewed screenshot matrix received a ship disposition with no material fixes; final human taste acceptance remains open. This presentation pass introduces no new model/provider or product-completeness claim.

## Template-to-document workflow extension — 2026-10-20

The next authorized delivery extends the existing Vue 3 application within that accepted visual family: browse a template, enter a dedicated document editor, check the content and export Word. The catalog's real starter covers open larger first-page previews with variables and sections in a collapsed disclosure. Its compact primary use action installs or reuses the workspace copy and opens `/generate/:templateId`; saved workspace choices and successful Word uploads also enter that editor directly. `/create` is now the import form and existing-template entry, superseding its four-cover gallery and inline editor composition.

The editor groups familiar short fields and dates separately from long content, preserves multiline and legacy values, and shows a live field-content check beside generation and download. That check does not render DOCX layout or pagination. Editing values or source records removes the previous download action until regeneration. Manual filling and export retain the existing model-free path; AI assistance still uses the configured model and existing retrieval contract.

Per-template drafts preserve declared field values, manual reference text, knowledge-base selection, retrieval preference and source records in `sessionStorage` under the compatible `quill-template-draft:v1:` prefix. Recovery is limited to the current browser tab; it is not server persistence or a cross-tab/account feature. Read/write failures produce feedback while manual editing and export remain available. The new field helper and draft composable are plain JavaScript; this work does not introduce Pinia or a full TypeScript migration.

This is the first main-workflow delivery. Reorganizing advanced knowledge features and extending free writing remain separate work. The latest bounded verification, finish-review status and rollout status are recorded in `docs/VALIDATION.md`; earlier review or deployment evidence does not establish those outcomes for this extension.
