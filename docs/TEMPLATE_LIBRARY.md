## User flow

- `/templates` combines workspace files and the starter library, with separate source tabs. Workspace files come first in the combined view. Search includes template names, descriptions and variable names; category choices reflect the current source's actual records. Grid/list and pagination remain available.
- Starter entries show first-page thumbnails rendered from their actual DOCX files. The cover button and “查看结构” open the same inline preview: a larger original first-page image, collapsed variables/sections, template details, original download and use action. Section names come from the definition that builds the Word file. Keyboard focus moves into the preview and returns to its trigger on close; Escape closes it. The image is a starter snapshot, with actual fonts and pagination subject to the downloaded Word file.
- Original starter DOCX files download without model setup or installation. The compact primary “使用模板” action stores one editable workspace copy and opens `/generate/:templateId`. Installation is idempotent, survives restarts, and chooses another name when a custom upload already owns the default name. Existing workspace metadata and files are preserved; workspace catalog entries also link directly to the dedicated editor.
- `/create` is the Word import route, with a native `.docx` file input and name, category and description fields beside a library entry and saved-template selector. The top “导入 Word” shortcut focuses native file selection. Unsupported file extensions are rejected before an upload API request. Successful upload and explicit saved-template selection navigate directly to the dedicated editor; no editor appears inline on `/create`. The earlier four-cover upload gallery is superseded. Generated documents continue to use the uploaded DOCX's original styles. Starter copies use A4, a title, a metadata table, headings, a header and a PAGE field.
- `/generate/:templateId` groups fields into basic information and long content. On load, draft restore, AI fill, explicit re-extraction or clear, familiar short fields use text inputs; date names ending in “日期” use native dates when empty or already ISO `YYYY-MM-DD`. Loaded values containing newlines or more than 120 characters use textareas, including values in otherwise short/date fields. Existing non-ISO dates stay editable as text for familiar short names or as a textarea otherwise; unknown field names stay multiline unless eligible for a native date. The selected control and group stay stable during manual typing, including crossing the length threshold or deleting a newline, to preserve focus. No value is truncated or reformatted.
- A live content-review panel shows the current declared fields and completion count beside generation and download. It checks field content, not DOCX pagination or final Word layout. The panels stack at 800px; the fixed mobile “核对与导出” shortcut focuses the actual generate button. Editing values or source records removes the old download action until a new document is generated. Explicit variable refresh preserves values for surviving field names.
- Per-template `sessionStorage` drafts use `quill-template-draft:v1:` plus the encoded template identity. They restore only currently declared field values, along with manual reference text, selected knowledge base, retrieval toggle and source records. Drafts belong to the current tab, with no server or cross-tab persistence claim. Read/parse and write failures display feedback while manual filling and export remain available. The route-path key remounts the editor when switching templates; drafts remain separate.
- Manual filling and export require no model or API key in the local deployment. AI filling retains the existing model dependency.

The workflow extends the current Vue 3 application using a shared `TemplateFields` component and plain JavaScript field/draft composables. It introduces neither Pinia nor a full TypeScript migration. Advanced knowledge reorganization and free-writing improvements are separate from this first main-workflow delivery.

## Authentic first-page thumbnails

The bounded raster asset exception consists of twelve PNGs in `frontend/public/template-previews`, one for each original starter, reused by the `/templates` catalog and its larger inline preview. `TemplateCover.vue` displays the first-page image at its original proportions inside a fixed-height, cropped catalog cover region; the larger preview removes that crop. Desktop catalog list view uses a compact cover; at or below 1100px list covers are hidden, with the structure action retained. These covers provide document orientation; download the DOCX for readable full content and editing. Variables and sections are available in a separate collapsed HTML disclosure within the preview.

The images originate only from the original definitions in `quill/template_library.py`, downloaded from the local library API and rendered with LibreOffice. No customer data, archived runtime templates or AI-generated imagery is used. Every PNG embeds source text in its `Source`, `Description` and `parameters` metadata; `provenance.json` records the template identifier/name, origin, full API definition and SHA256 of the exact downloaded DOCX. Preserve both embedded metadata and the manifest when updating assets. The DOCX hash identifies that downloaded artifact; regeneration can differ because DOCX packaging metadata, renderer versions and fonts can differ.

These are starter first-page snapshots, rather than pagination or fidelity guarantees. Fonts must be available to the renderer, including Chinese glyph coverage; missing fonts can produce substitution, unreadable glyphs or different line breaks. LibreOffice and Microsoft Word may paginate differently. The gallery crop does not expose the whole page, later pages are not included, and filled or edited documents can flow differently. Custom workspace uploads do not receive captured thumbnails through this utility. If a cover fails to load, the shared component shows the actual template name, up to three real section titles and an explicit unavailable-image message; structure and use actions remain available.

## Regenerating thumbnails

Run from the repository root against a local DocuGen API serving the starter library. The utility issues GET requests to `/api/template-library` and `/api/template-library/<id>/download`, writes temporary DOCX/render outputs and replaces the PNGs and manifest in the chosen output directory. It does not install templates, change workspace records or call a model. Its current HTTP client sends no workspace access key; use a local loopback deployment with the optional key empty.

Prerequisites: Python with Pillow, a compatible `render_docx.py` (for example the Codex documents skill renderer), LibreOffice/`soffice`, Poppler (`pdfinfo` and `pdftoppm`) and the renderer's Python dependencies, including `pdf2image`. Ensure the runtime can locate the required executables and fonts. Supply the renderer's path explicitly; it is external developer tooling rather than a bundled repository dependency.

```sh
python scripts/export_template_previews.py \
  --base-url http://127.0.0.1:8080 \
  --renderer /path/to/documents/render_docx.py \
  --output frontend/public/template-previews
```

The renderer must accept a DOCX path with `--output_dir`, `--width 420` and `--height 594`, and produce `page-1.png`. The utility renders the document then retains the first page, converting it to RGB and embedding origin metadata through Pillow. An optional `--embed-tool /path/to/impeccable-launcher` additionally invokes that tool's `embed-prompt` command; the three source metadata fields and manifest are written even without it. After regeneration, inspect all twelve images for legibility and source agreement before accepting updated assets. This regeneration is developer work, not a runtime requirement for viewing the shipped gallery.
